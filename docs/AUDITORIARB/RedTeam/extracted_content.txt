🧪 MISIÓN 1 — FROM ZERO: Reproducibilidad

Resultado: 🟢 Reproducible. El primer intento con git clone + docker compose up -d --build levanta el entorno completo. Después del primer arranque (lento), arranques subsecuentes son segundos.

1.1 Resumen ejecutivo

El README.md está entre los mejores que he visto para un proyecto de este tamaño: explica arquitectura, requisitos, comandos, variables de entorno, modelo de grafo, endpoints, decisiones técnicas, respaldo/restauración y pruebas. El equipo hizo el trabajo de documentación.

1.2 Pasos realizados

Lectura completa del README.md (29.7 KB).

Inspección de docker-compose.yml (6.3 KB), docker-compose.dev.yml, Dockerfile de backend y frontend.

Verificación de los healthcheck de cada servicio.

Inspección del script keys-init que genera claves JWT y VAPID al primer arranque.

1.3 Hallazgos

H-01 · 🟡 El primer arranque tarda porque MinIO se compila desde código fuente

Evidencia: docker-compose.yml → minio: { build: { context: ./infra/minio, target: minio } }. Es la imagen base, no se usa minio/minio:latest.  Impacto: El primer up --build tarda varios minutos (descargar imágenes Maven, compilar backend, compilar MinIO). El README lo menciona pero no cuantifica.  Recomendación: Documentar tiempo esperado (~10 min en hardware modesto) o cambiar a minio/minio:latest si la compilación no es necesaria.

H-02 · 🟢 Si se borra el volumen app_keys, todos los JWT y suscripciones push caducan

Evidencia: docker-compose.yml job keys-init (líneas 73-103): genera el par RSA 2048 + VAPID solo si no existe. chmod 644 sobre las claves (ver H-10 en Misión 4).  Impacto: Operacional: un operador que corre docker compose down -v por error invalida todos los tokens y suscripciones. El README lo documenta pero el sistema no avisa.  Recomendación: Agregar un script rotate-keys.sh que migre tokens a una nueva clave pública sin forzar re-login (rotación de claves con período de gracia).

1.4 Conclusión de la misión

🟢 Reproducible. La promesa del README se cumple. El único punto de fricción real es la paciencia en el primer arranque.

2.4 Hallazgos

H-03 · El feed puede reportar más comentarios que los visibles en el hilo

Evidencia: CommentRepository.java:23 MAX_THREAD_COMMENTS = 200. La consulta C1 reporta COUNT { (p)<-[:EN]-(:Comentario)<-[:RESPONDE_A*0..50]-(:Comentario) }, que cuenta el total. Si un post tiene 350 comentarios, el feed dirá "350" pero la vista de detalle solo traerá 200.

Impacto: Confusión menor. El frontend lo señala correctamente con la regla "Si el padre de una respuesta quedó fuera del recorte, el frontend la presenta como comentario principal para no ocultarla".

Recomendación: Documentar en el README o devolver un flag truncated: true en la respuesta de comentarios.

H-04 · 🟡 No hay bandeja de notificaciones

Evidencia: frontend/src/pages/SettingsPage.tsx (sin sección de bandeja), frontend/public/sw.js solo dispara showNotification.  Impacto: Si el usuario descarta la notificación nativa, no tiene forma de revisar qué se perdió. Común en redes sociales modernas.  Recomendación: Agregar GET /api/notificaciones (eventos de posts de seguidos, reacciones a tus posts, comentarios a tus posts) y vista en la SPA. Es una buena Misión 7.

☠️ MISIÓN 3 — CODE AUTOPSY

Resultado: 🟡 Aprobado con reservas. El backend tiene buena estructura por capas y un manejo honesto de eventos asíncronos. Los puntos a revisar son: el tamaño de PostService, el acoplamiento de contenido entre PostRepository y CommentRepository, el field injection en ChatSocket, y el spanglish estructural.

3.1 Resumen ejecutivo

El backend es Quarkus 3.33 LTS + Java 21. La organización de paquetes refleja features (auth, chat, comentarios, feed, media, notificaciones, posts, shared, social, usuarios) y la convención es Resource → Service → Repository → Driver. La mayoría de las clases ya migraron a constructor injection; quedan dos casos a actualizar.

3.2 Acoplamiento sano (lo que está bien)

Eventos asíncronos:PostService.create() emite PostCreated con events.fireAsync y no espera al push. Si mañana sacás las notificaciones, POST /api/posts ni se entera. Es el ejemplo de bajo acoplamiento del proyecto. PostService.java:71-77.

Inyección por constructor: Todos los Resources y Services del backend usan constructor injection. Ejemplos: AuthResource, AuthService, ChatService, PostService, CommentService, PushSubscriptionService. El contenedor CDI es explícito.

Interfaces para infraestructura:MediaStorage es una interfaz; PostService solo conoce MediaStorage, no S3MediaStorage. Si mañana cambias a Azure Blob, no tocás PostService. MediaStorage.java:6-10.

Dedupe en ChatSessions:LinkedHashMap con putIfAbsent y eviction al llegar a 4096 entries. Garantiza que un mensaje entregado por Redis y por la propia suscripción local no se envíe dos veces. ChatSessions.java:31-37.

Seed auto-verificable:seed-demo.mjs:174-195 corre las 8 consultas Cypher al final y aborta si alguna falla. Es el equivalente a "tests de integración del happy path".

3.3 Acoplamiento que va a doler

H-05 · 🟠 PostService con 5 dependencias y método orquestador grande

Evidencia: backend/src/main/java/com/redsocial/posts/PostService.java:21-26:

public PostService(PostRepository repository, MediaStorage storage, ImageValidator images,         Event<PostCreated> events, PostAssembler assembler) {

El método create() (líneas 38-83) valida texto, valida imagen, sube a storage, escribe en Neo4j, dispara evento, ensambla respuesta. 46 líneas con cuatro try/catch para rollback.

Impacto: El blast radius es enorme. Si cambia la subida de imágenes, tocás el mismo método que crea posts. Si cambia la serialización del evento, también. Si cambia el contrato de Neo4j, también.

Recomendación: Partirlo:

class PostCreator {     private final TextValidator text;     private final PostImageAttacher images;     private final PostPersister persister;     private final PostEventPublisher events;     PostResponse create(CreatePostCommand cmd) {         text.validate(cmd.text());         var stored = persister.commit(cmd, images.attach(cmd.file()));         events.publish(stored);         return assembler.response(stored);     } }

PostImageAttacher orquesta ImageValidator + MediaStorage + rollback. PostPersister se reduce a una transacción Neo4j. El método create queda en 8 líneas.

H-06 · 🟡 PostRepository.PUBLIC_FIELDS consume CommentRepository.COUNT_OF_POST

Evidencia: PostRepository.java:23-29:

public static final String PUBLIC_FIELDS = """         ...         %s AS comentarios""".formatted(CommentRepository.COUNT_OF_POST);

Acoplamiento de contenido: una constante de otro paquete aparece en el SQL formateado. Si mañana cambias cómo se cuentan los comentarios (sumar respuestas indirectas, por ejemplo), recompilás posts aunque no hayas tocado su lógica.

Impacto: Bajo en el día a día (la query no cambia seguido), alto cuando toque migrar. Es una static final compartida que rompe el principio "cada paquete sabe de sí mismo".

Recomendación: Duplicar el string en PostRepository o mover COUNT_OF_POST a shared/cypher/. La duplicación es preferible al acoplamiento de imports cruzados.

H-07 · 🟡 AuthService depende de UserService (servicio) en vez de UserRepository

Evidencia: AuthService.java:23-26, 32-49:

public AuthService(AuthRepository repository, UserService users) {     this.repository = repository;     this.users = users; } // register() hace: return users.profile(id);

Acoplamiento transitivo: un cambio en UserService.profile() puede romper AuthService.register() sin tocar el paquete auth.

Impacto: Un UserService que hoy solo expone profile() mañana puede crecer y arrastrar dependencias que auth no necesita.

Recomendación: AuthService debería leer del UserRepository directamente (que es lo que hace para escribir). Si la lógica de profile() es no trivial, moverla a un ensamblador compartido o a un método del repositorio.

H-08 · 🟡 ChatSocket con field injection

Evidencia: ChatSocket.java:31-38:

@Inject ChatService service; @Inject ChatSessions sessions; @Inject JsonWebToken jwt; @Inject ObjectMapper json;

El resto del backend migró a constructor. ChatSocket quedó atrás.

Impacto: Inmutabilidad perdida (campos no final), dependencias implícitas (no se ven en el constructor), testabilidad peor (necesitás levantar CDI para mockear).

Recomendación: Migrar a constructor injection. Cambio mecánico, ~10 minutos.

H-09 · 🟢 Spanglish estructural

Evidencia:

Paquetes en español: comentarios, notificaciones (ClavePublica.java, SuscripcionRequest.java, Sugerencia.java).

Records con campos en español: CommentRequest(texto, respondeA), CommentResponse(texto, fecha, autor, respuestas).

Métodos en inglés sobre esos mismos objetos: create(), thread(), save(), history().

Comentarios en inglés: // Shares the /posts root..., // Business error thrown....

Mensajes al usuario en español: mensaje no message.

Impacto: El costo cognitivo se duplica: para encontrar algo tenés que adivinar si es text o texto, parentId o respondeA. Además, el dominio "miente": DDD dice que el código tiene que hablar el idioma del negocio. Si tu negocio es una red social latina, respondeA está bien; entonces create debería ser crear.

Recomendación: Tres reglas documentadas en el README:

Código (identificadores + comentarios + commits): TODO en inglés. text, parentId, FollowerCount.

Lo que ve el usuario (mensajes de error, copy del frontend, descripciones OpenAPI): TODO en español. Ya lo hacés con mensaje y content/copy.

No migrar lo viejo de golpe. Congelá la regla para código nuevo desde hoy. Lo viejo se migra cuando toque cada módulo por otra razón.

3.4 Conclusión de la misión

🟡 Aprobado con reservas. El código tiene alma de un sistema distribuido bien pensado. Las reservas son:

🔐 MISIÓN 4 — BREAK IT: Seguridad y pentesting controlado

Resultado: 🟠 Aprobado con reservas críticas. Se identifica una vulnerabilidad crítica (chmod 644 sobre privateKey.pem) que debe corregirse antes de cualquier despliegue fuera de localhost. El resto son endurecimientos progresivos.

4.1 Resumen ejecutivo

El sistema tiene un diseño de seguridad razonable: tokens JWT firmados con RSA, contraseña hasheada con bcrypt, push con VAPID, validaciones de entrada en cada endpoint, rate limiting en Nginx. Pero hay tres puntos rojos: la clave privada compartida con permisos demasiado abiertos, un timing attack detectable en el login, y la ausencia de Content-Security-Policy en el proxy.

4.2 Hipótesis → Prueba → Evidencia → Impacto

H-10 · 🔴 CRÍTICA — Clave privada del JWT world-readable

Hipótesis: El volumen app_keys con chmod 644 permite que cualquier proceso en el host o contenedor con acceso al volumen firme tokens falsos.

Prueba: Lectura directa de docker-compose.yml:

keys-init:   ...   command: |     ...     chmod 644 /keys/*   # ← línea 102 volumes:   - app_keys:/keys:ro

Evidencia: docker-compose.yml:102. La clave privada queda con permisos rw-r--r-- (644). Cualquier proceso con acceso de lectura al volumen puede usarla para firmar JWTs válidos.

Impacto: Crítico. Un atacante con acceso de lectura al host (compromiso de otro servicio, container escape, error de backup que termina en un bucket público) puede emitir tokens para cualquier subject y leer/escribir datos en nombre de cualquier usuario.

Recomendación:

Cambiar chmod 644 por chmod 600 en el job keys-init.

Cambiar el umask del proceso backend a 077 antes de leer.

Auditar quién tiene acceso al host y al volumen con docker volume inspect app_keys.

Documentar la rotación de claves (regenerar privateKey.pem invalida todos los JWTs).

H-11 · 🟠 Alta — User enumeration por timing en AuthService.login()

Hipótesis: Si el usuario no existe, el Optional se filtra sin correr bcrypt.matches. La rama "no existe" termina antes que "existe + contraseña mala", y la diferencia es detectable con un número suficiente de muestras.

Prueba: Lectura directa de AuthService.login():

public LoginResponse login(LoginRequest request) {     Credentials credentials = repository.findCredentials(request.username())             .filter(c -> BcryptUtil.matches(request.password(), c.passwordHash()))             .orElseThrow(() -> { ... });     ... }

Evidencia: AuthService.java:51-58 + AuthRepository.java:51-66 (findCredentials retorna Optional<Credentials>). Si el Optional está vacío, BcryptUtil.matches no se ejecuta. Bcrypt con factor 10-12 toma ~100-300 ms; el retorno vacío toma ~5-20 ms (solo el round-trip a Neo4j).

Impacto: Un atacante puede enumerar usernames válidos midiendo el tiempo de respuesta, y luego enfocar el brute force en esos. El rate limit de Nginx (20 r/m) ayuda pero no cierra el canal.

Recomendación: Forzar siempre la corrida de bcrypt:

String hash = repository.findCredentials(request.username())         .map(Credentials::passwordHash)         .orElse(BCRYPT_OF_DUMMY); // hash precomputado de "no-user" if (!BcryptUtil.matches(request.password(), hash)) {     LOG.warnf("Inicio de sesión fallido usuario=%s", safeUsername(request.username()));     throw ApiException.unauthorized(...); }

El BCRYPT_OF_DUMMY se calcula una vez al arranque y se guarda. Así ambos caminos demoran lo mismo.

H-12 · 🟠 Alta — Sin Content-Security-Policy en Nginx

Hipótesis: Un XSS en el frontend podría cargar scripts arbitrarios desde cualquier origen, robando el JWT de localStorage.

Prueba: Lectura de frontend/nginx.conf:

add_header X-Content-Type-Options "nosniff" always; add_header X-Frame-Options "DENY" always; add_header Referrer-Policy "strict-origin-when-cross-origin" always;

No hay Content-Security-Policy.

Evidencia: frontend/nginx.conf en el bloque server. Tres headers presentes, CSP ausente.

Impacto: Un comentario con un payload XSS (texto sin escape, markdown mal procesado, dangerouslySetInnerHTML) puede cargar un script externo que lea localStorage.getItem("nodouni.session") y exfiltre el JWT.

Recomendación: Agregar una CSP estricta. Como el frontend es Vite + Tailwind sin assets cross-origin:

add_header Content-Security-Policy "     default-src 'self';     script-src 'self';     style-src 'self' 'unsafe-inline';     img-src 'self' data: blob:;     connect-src 'self' wss: HYPERLINK "https://*.push.services.mozilla.com" https://*.push.services.mozilla.com https://fcm.googleapis.com https://updates.push.services.mozilla.com;     frame-ancestors 'none';     base-uri 'self';     form-action 'self'; " always;

Los endpoints push (Mozilla, FCM, Apple) requieren connect-src permisivo para esos orígenes específicos.

H-13 · 🟡 JWT en localStorage (vulnerable a XSS)

Evidencia: frontend/src/lib/session.ts:3 SESSION_KEY = "nodouni.session". api.ts:26,31 lo lee y lo manda en cada request.  Impacto: Si H-12 no se cierra, H-13 amplifica el daño. Aceptable con JWT de 24h y sin refresh, pero no guardar nada sensible además del token en localStorage.  Recomendación: Documentar en el README. Considerar migrar a cookie httpOnly + SameSite=Lax con CSRF token cuando se implemente refresh.

H-14 · 🟡 El frontend desloguea en cualquier 401 sin distinguir vencido vs inválido

Evidencia: frontend/src/lib/api.ts:40-41:

if (response.status === 401 && token && getSession()?.token === token)     setSession(null);

Impacto: Un 401 transitorio (skew de reloj, request con token viejo en otra pestaña) desloguea al usuario sin aviso. Con JWT de 24h y sin refresh, ese logout duele.  Recomendación: Distinguir:

WWW-Authenticate: Bearer error="invalid_token" → token malformado o mal firmado → logout.

Sin error específico y tokenExpiresAt(token) < now + 30s → pre-expirado → intentar refresh (cuando exista).

Otros 401 → mostrar mensaje, no desloguear.

H-15 · 🟡 ImageValidator no acepta WebP/HEIC

Evidencia: backend/src/main/java/com/redsocial/media/ImageValidator.java:22-25:

private static final Map<String, ImageType> TYPES = Map.of(         "png", new ImageType("image/png", "png"),         "jpeg", new ImageType("image/jpeg", "jpg"),         "gif", new ImageType("image/gif", "gif"));

Impacto: UX. Los celulares modernos sacan WebP/HEIC por defecto. El usuario tiene que convertir antes de subir.  Recomendación: Agregar "webp" → image/webp y opcionalmente HEIC (con libheif). Requiere actualizar la imagen base del backend o agregar la dependencia nativa.

H-16 · 🟡 Defaults que no pueden llegar a prod sin alerta

Evidencia: docker-compose.yml usa VAPID_SUBJECT: ${VAPID_SUBJECT:-mailto:admin@example.com} y NEO4J_PASSWORD: ${NEO4J_PASSWORD:-devpassword}.  Impacto: Si el operador olvida cambiar el .env antes de desplegar, el sistema funciona pero con credenciales de dev.  Recomendación: Agregar un check de arranque en Quarkus:

@ApplicationScoped public class ProdSecretsCheck {     void onStart(@Observes StartupEvent e) {         if (ConfigSource.from("prod") &&             (config.neo4jPassword().equals("devpassword") ||              config.vapidSubject().contains("example.com"))) {             throw new IllegalStateException("Dev defaults still set in prod profile");         }     } }

H-17 · 🟡 Sin observabilidad distribuida

Evidencia: No hay dependencia de quarkus-micrometer ni quarkus-opentelemetry en el pom.xml. No se propaga X-Request-Id en Nginx.  Impacto: Con 2 réplicas + round robin, cuando un usuario reporta "me falló el post", no podés saber si fue backend-1 o backend-2 salvo por GET /info o el upstream_addr del log de Nginx.  Recomendación:

Agregar quarkus-micrometer-registry-prometheus + endpoint /q/metrics.

En Nginx: proxy_set_header X-Request-Id $request_id; (usar uuid4 si $request_id no está habilitado).

En el backend: loggear requestId en cada línea.

Incluir app.instance-id en cada log (ya está en application.properties).

H-28 · 🟠 Credencial inmutable: sin cambio/recuperación de contraseña ni revocación

Hipótesis: La contraseña es el único factor de autenticación y es inmutable. Si se filtra, la víctima no puede cambiarla (no hay endpoint) ni expulsar al atacante (el JWT stateless dura 24 h y no se puede revocar).

Prueba: Inspección de AuthResource.java:23,36,48 — @Path("/auth") solo expone /registro y /login; ninguna ruta de contraseña. AuthService.java:51-64 — login() firma el JWT; no hay método de cambio de contraseña. application.properties:23 — smallrye.jwt.new-token.lifespan = 86400 (24 h). frontend/src/context/AuthProvider.tsx:68-71 — logout solo borra el estado local.

Evidencia: backend/src/main/java/com/redsocial/auth/AuthResource.java:23,36,48, backend/src/main/java/com/redsocial/auth/AuthService.java:51-64, backend/src/main/resources/application.properties:23, frontend/src/context/AuthProvider.tsx:68-71.

Impacto: Alta. El acceso del atacante es irrevocable hasta por 24 h por token emitido, y permanente mientras el atacante pueda volver a loguearse con la contraseña comprometida. "Cerrar sesión" en el cliente no invalida el token en el servidor.

Recomendación: Añadir tokenVersion en (:Usuario) como claim validado por petición contra el JWT, y exponer PUT /api/auth/password (solicitando la contraseña actual) que incremente este contador. Así, al cambiar la contraseña se invalidan instantáneamente todos los tokens previos en ambas réplicas.

4.3 Lo que SÍ está bien

Nginx limita correctamente:auth_zone: 20r/m burst=40 para /api/auth/*, write_zone: 120r/m burst=60 para métodos no-GET fuera de auth. Lecturas no consumen cuota.

El SW no loggea tokens:frontend/public/sw.js no guarda el JWT ni la query.

client_max_body_size 6m está bien calibrado para el límite de 5 MiB del ImageValidator.

Push endpoint URL validador:PushEndpointValidator rechaza local hostnames, IPv6, y exige HTTPS + dominio público.

ChatTokenAuthentication con cap de 16384 chars en el query param del WS.

Lock distribuido en suscripciones push:PushRepository.subscribe usa executeWrite con LOCK_USER (incrementa pushSubscriptionVersion) para serializar suscripciones concurrentes desde ambas réplicas.

Web Locks API en el frontend:services/push.ts usa navigator.locks.request("nodouni-push", ...) para evitar doble subscribe concurrente.

4.4 Conclusión de la misión

🟠 Aprobado con reservas críticas. Corregir H-10 (chmod 600) antes de cualquier despliegue real es obligatorio. H-11, H-12 son endurecimientos importantes. El resto puede esperar al siguiente sprint.

5.2 Flujos evaluados

5.2.1 Registro

Pasos: Pantalla /registro → completar username, email, password, nombre → POST /auth/registro → redirige a /login.

Fricción H-18 (🟠): El registro es de dos round-trips. El backend devuelve Profile, no token. El usuario tiene que volver a tipear usuario y contraseña.

Evidencia:frontend/src/services/users.ts:14-22 (register retorna Profile, no token). AuthResource.java:33-40 (register retorna Profile). El README dice "registro e inicio de sesión" como funcionalidades, no las fusiona.

5.2.2 Login

Fricción menor: No hay "olvidé mi contraseña" (ver H-04 equivalente en Misión 2).

Positivo:AuthProvider arma un timer con tokenExpiresAt(session.token) para auto-desloguear cuando vence. Pero ese timer se reinicia en cada useEffect, lo que significa que no hay chequeo proactivo del lado del cliente mientras hay actividad.

5.2.3 Crear publicación

Pasos:/feed → click "Publicar" → PostComposer con textarea + upload de imagen → enviar.

Fricción H-19 (🟠): Si el usuario refresca la pestaña, navega a otra ruta, o cambia de cuenta, el texto y la imagen se pierden sin aviso. No hay sessionStorage que los respalde.

Evidencia:frontend/src/components/PostComposer.tsx no tiene un useEffect que persista. El subagente de revisión lo confirmó.

Recomendación: Persistencia debounced en sessionStorage (lifespan: la sesión), y conteo con Intl.Segmenter para graphemes.

5.2.4 Seguir a un usuario

💥 MISIÓN 6 — CHAOS MODE

Resultado: 🟢 Buena resiliencia, con gaps de testing. El sistema tiene retry exponencial en WS, retry con backoff en REST, dedupe en ChatSessions, y reconexión en RedisChatBroker. Pero faltan tests de los caminos de fallo más importantes (token JWT expirado, race en registro, reconexión WS con mensajes en vuelo).

6.1 Resumen ejecutivo

La resiliencia se construyó por dos lados: el backend con reconexión automática (Redis broker) y el frontend con reintentos y backoff (WS, history, api en general). El test suite es sólido en chat y débil en auth/posts.

6.2 Modos de fallo analizados

6.2.1 Neo4j se detiene temporalmente

Comportamiento esperado: El backend no puede escribir ni leer. Los requests devuelven 500 ERROR_INTERNO (vía ExceptionMappers.unexpected).

Comportamiento real:ExceptionMappers.unexpected loguea el error y devuelve ERROR_INTERNO. El frontend reintenta history 3 veces (H-XX).

Recuperación: Cuando Neo4j vuelve, el frontend no necesita refrescar manualmente: el próximo request funciona. Los health checks de Docker reinician automáticamente el contenedor.

Gap: No hay circuit breaker. Si Neo4j se demora 30s, cada request espera 30s antes de fallar. Con 2 réplicas, el LB no las saca de rotación.

6.2.2 Redis se detiene

Comportamiento esperado: El chat no se entrega entre réplicas. El historial queda en Neo4j.

Comportamiento real (backend):ChatService.send() intenta broker.publish(saved).await().atMost(Duration.ofSeconds(2)) y si falla, loguea warnf("Redis unavailable..."). Después llama sessions.deliver(saved) local, así que el emisor siempre ve su mensaje.

Recuperación:RedisChatBroker (RedisChatBroker.java:80-86) reconecta con timer de 1s al detectar disconnected(). Backoff lineal, no exponencial.

Gap: El receptor en otra réplica no ve el mensaje en vivo. Solo lo ve al recargar historial por REST. Esto es un tradeoff conocido del diseño, documentado en el README, pero el usuario lo vive como bug.

6.2.3 Backend-1 se reinicia

Comportamiento esperado: Los sockets conectados a backend-1 se cierran. El frontend reconecta.

Comportamiento real:useChatConnection tiene backoff 1s → 2s → 4s → ... → 30s. Al reconectar, el handshake con ?token= re-valida el JWT. Si el token venció, el backend cierra con 1008 Usuario no disponible o 1008 JWT vencido.

Recuperación de mensajes perdidos:reconnect() en ChatProvider recarga chat.list y vuelve a llamar loadHistory(id) para cada conversación cargada. Excelente.

Gap: Los mensajes enviados durante el reinicio se pierden del feed en vivo (el send() en el frontend retorna false si el socket no está OPEN). No hay cola de outbox en el cliente.

6.2.4 Neo4j se corrompe (constraint violation masiva)

Comportamiento: Las constraints están como IF NOT EXISTS (ver Neo4jConstraints.java:18-25). Si se reinicia Neo4j con una versión anterior del schema, las constraints se vuelven a crear. Bien.

Gap: Si dos requests concurrentes intentan crear el mismo username, el primero gana y el segundo recibe Neo.ClientError.Schema.ConstraintViolationFailed. El AuthService lo captura y lo traduce a 409 USERNAME_EN_USO. Pero hay una ventana mínima donde ambos pueden leer "no existe" antes de que el constraint valide.

6.2.5 Token JWT expira

Comportamiento backend: El endpoint protegido responde 401 vía ExceptionMappers.authenticationFailed. El header WWW-Authenticate: Bearer está presente.

Comportamiento frontend:api.ts:40-41 desloguea en cualquier 401. El AuthProvider arma un timer de tokenExpiresAt que se ejecuta cuando vence, llamando setSession(null). El doble deslogueo es idempotente, así que no hay problema funcional, pero la UX es brusca.

Gap de test (H-25): No hay un test que pruebe "token vencido → 401 → UX de cierre de sesión". El test verifica la duración (exp - iat = 86400) pero no el camino de fallo.

6.2.6 Acciones concurrentes (reaccionar dos veces al mismo post rápido)

Comportamiento:PostService.react usa MERGE en Cypher con ON CREATE SET. La segunda llamada no duplica la relación, solo actualiza el timestamp. Idempotente.

Comportamiento frontend:PostCard.toggleReaction tiene if (reactionBusy) return y setReactionBusy(true). Seguro.

6.2.7 Frontend con un servicio no disponible (Neo4j caído)

El frontend hace await fetch("/api/..."). Si el backend está arriba pero Neo4j caído, recibe 500. api.ts:30 lo traduce a ApiError(0, { error: "CONEXION", mensaje: copy.connectionError }). Falla genérica, no específica.

El feed no se distingue entre "Neo4j caído" y "backend caído". El usuario ve "Error de conexión" sin contexto.

6.3 Hallazgos

H-25 · 🟡 No hay test de JWT expirado

Evidencia: backend/src/test/java/com/redsocial/auth/AuthResourceTest.java verifica exp - iat = 86400 pero no prueba el flujo "vencido → 401 → UX".  Impacto: El camino más probable a 24h vista no está cubierto.  Recomendación: Test con un JWT firmado con lifespan=1s + Thread.sleep(1500) + request → assert 401.

H-26 · 🟡 No hay test de race en POST /auth/registro

Evidencia: AuthResourceTest.java cubre duplicados secuenciales (409), pero no concurrentes.  Impacto: Ventana mínima donde dos requests podrían pasar la lectura "no existe" antes de la escritura constraint. Depende del aislamiento de Neo4j.  Recomendación: Test con ExecutorService lanzando 4 registros en paralelo con el mismo username → assert que solo 1 devuelve 201 y 3 devuelven 409.

H-27 · 🟢 RedisChatBroker reconecta con backoff lineal fijo

Evidencia: RedisChatBroker.java:80-86 vertx.setTimer(1000, ...). Sin jitter, sin backoff exponencial.  Impacto: Con 2 réplicas no hay problema. Con 20+ en una tormenta de red, todas las reconexiones golpean Redis al mismo tiempo. Aceptable hoy.  Recomendación: Cambiar a min(1000 * 2^n + jitter, 30000).

6.4 Lo que SÍ está bien

RedisChatBroker tiene reconexión robusta: la lógica disconnected() → setTimer(1000, connect) se ejecuta dentro de synchronized y verifica stopped para no fugar timers. Es código defensivo serio.

useChatConnection con backoff exponencial: 1s → 2s → 4s → ... → 30s. Es la práctica recomendada para clientes WebSocket.

chat.history reintenta solo lecturas idempotentes: 3 intentos con delay incremental (1s, 2s), solo en errores de red (0, 502, 503, 504). Nunca reintenta un POST, lo que evita duplicar posts o comentarios.

Tests de chat son sólidos:ChatSocketTest.java cubre tokens expirados, tokens con issuer incorrecto, token doble (?token=x&token=y), conexión concurrente, fan-out a múltiples sesiones, failedBroker (mensaje se persiste localmente aunque Redis esté caído). El test suite más maduro del proyecto.

Tests de chat cubren idempotencia concurrente:ChatResourceTest.createIsIdempotentInBothDirectionsEvenConcurrently lanza 6 requests en paralelo y verifica una sola conversación.

Nginx proxy_next_upstream con cap de 2 tries y timeout 2s/5s: si una réplica está caída, el LB no se queda esperando.

Seed auto-verificable: aborta el seed si alguna de las 8 consultas falla.

6.5 Conclusión de la misión

🟢 Buena resiliencia, con gaps de testing. El sistema degrada con elegancia (mensajes en historial, reconexión automática, dedupe). Faltan tests de los caminos de fallo más comunes (JWT expirado, race en registro), pero la implementación parece sólida.

A.1 Token, sesión y autenticación (M4, M5)

"Es un solo token, sin refresh. LoginResponse.java es un record con un solo campo token, y AuthService.login() lo genera con Jwt.subject(id).upn(username).sign(). No hay ningún RefreshToken en el grafo — busqué y no existe. El backend mismo lo dice en AuthResource.java:20-21: 'el login emite el JWT que todo endpoint privado requiere; el servidor no guarda sesión'. Es stateless puro, con vida útil de 24h."

Confirmado. AuthService.java:51-58 genera el JWT con Jwt.subject(credentials.id()).upn(credentials.username()).sign(). application.properties define smallrye.jwt.new-token.lifespan=${JWT_LIFESPAN_SECONDS:86400} (24h).

"Y sí, vive en localStorage. frontend/src/lib/session.ts:3 define SESSION_KEY = "nodouni.session" y guarda el JSON { token, user } ahí. Después frontend/src/lib/api.ts:26,31 lo lee con getSession()?.token y lo manda en cada request como Authorization: Bearer <token>. Si el backend devuelve 401, api.ts:40-41 hace setSession(null) — o sea, te desloguea."

Confirmado y elevado a H-13 (🟡, M4) y H-14 (🟡, M5).

A.2 Acoplamiento sano y malsano (M3)

"Lo sano: cada feature tiene Resource → Service → Repository con inyección por constructor. PostNotifier.java:36 escucha PostCreated con @ObservesAsync. PostService dispara el evento con fireAsync y NO espera el push. MediaStorage es interfaz."

Confirmado y referenciado en la sección 3.2 de M3.

"Lo acoplado de más: PostService.java:22-26 tiene 5 dependencias. AuthService → UserService → UserRepository. PostRepository.PUBLIC_FIELDS:23-29 importa CommentRepository.COUNT_OF_POST. Hotspots con fan-in altísimo: ExceptionMappers.api (fan-in 52), PostRepository.react (51), lib/api.ts:api (24)."

Confirmado y elevado a H-05 (🟠), H-06 (🟡), H-07 (🟡) en M3.

A.3 Field injection en ChatSocket (M3)

"Esos 4 @Inject en campos tendrían que ser constructor injection con final."

Confirmado y elevado a H-08 (🟡) en M3.

A.4 Spanglish estructural (M3)

"Paquetes en español: comentarios, notificaciones (ClavePublica.java, SuscripcionRequest.java, Sugerencia.java). Records con campos en español: CommentRequest(texto, respondeA). Métodos en inglés sobre esos mismos objetos: create(), thread(), save(), history(). Mensajes al usuario en español: 'El usuario no existe'."

Confirmado y elevado a H-09 (🟢) en M3, con la recomendación concreta de tres reglas documentadas.

A.5 WebSocket pegajoso vs REST libre (M3, M6)

"Un WS conectado NO vuelve a pasar por el balanceador. El round robin elige UNA sola vez: en el handshake. El problema real es el OTRO caso: tu amigo manda un mensaje y su request REST cae en backend-2. ¿Cómo te llega? Por Redis. ChatService.send() hace las DOS cosas: broker.publish(saved) al canal Redis + sessions.deliver(saved) local. Cada réplica está suscripta."

Confirmado. ChatService.send() (líneas 60-72): hace repository.save() → broker.publish() → sessions.deliver(). RedisChatBroker suscribe commands.subscribe(CHANNEL, sessions::deliver, this::disconnected, ...). Excelente diseño.

A.6 Escalabilidad: chat dedicado o proxy (M3, M6)

"Si el chat escala distinto que el REST, SÍ, backend dedicado. Hoy tus 2 réplicas son monolitos clonados. Si el problema es 'nginx dentro del frontend me hace ruido', SÍ, proxy dedicado (Traefik/Caddy). Lo que NO haría: ip_hash."

Recomendación incorporada a la sección 6.2.1 y 6.2.2 de M6.

A.7 Permisos de clave privada (M4, Crítica)

"La privada del JWT queda legible por todos — ❌ lo más grave. docker-compose.yml:102 hace chmod 644 /keys/* y monta app_keys:/keys:ro en AMBOS backends. Tiene que ser 600 (o 640 con grupo), nunca 644."

Confirmado y elevado a H-10 (🔴 CRÍTICA) en M4.

A.8 Registro sin logueo (M5)

"El registro no loguea — ⚠️ fricción UX. AuthService.register():32-49 devuelve Profile, no token. El frontend (users.register → api) obliga a registrarse Y después loguearse."

Confirmado y elevado a H-18 (🟠) en M5.

A.9 401 desloguea sin piedad (M4, M5)

"El 401 te patea la sesión sin piedad — ⚠️. api.ts:40-41: cualquier 401 con el token actual hace setSession(null). Distinguí expirado vs inválido antes de borrar."

Confirmado y elevado a H-14 (🟡) en M4.

A.10 Imágenes sin WebP/AVIF (M5)

"Imágenes sin WebP/AVIF — ⚠️ gap de producto. ImageValidator:22-25 solo acepta png/jpeg/gif (5 MiB, 20 MP). Los celulares modernos sacan WebP/HEIC por defecto."

Confirmado y elevado a H-15 (🟡) en M4.

A.11 Redis 100% efímero (M6)

"Redis 100% efímero — ✅ bien, pero asumí la ventana. redis: --save "" --appendonly no + tmpfs: correcto para pub/sub, pero si Redis cae justo en el publish, el mensaje queda en Neo4j y solo se entrega local. El receptor lo ve al recargar historial, no en vivo."

Confirmado. Documentado en la sección 6.2.2 de M6.

A.12 Defaults que no pueden llegar a prod (M4)

"VAPID_SUBJECT=mailto:admin@example.com y NEO4J_PASSWORD=devpassword funcionan en dev, pero nada te frena si se te olvida cambiarlos."

Confirmado y elevado a H-16 (🟡) en M4.

A.13 Sin observabilidad distribuida (M4)

"Sin observabilidad distribuida — ⚠️. Tenés /q/health y INSTANCE_ID como env, pero no veo Micrometer/OpenTelemetry ni correlation-ID en los logs."

📎 Anexo B — Hallazgos propios que el equipo original no tenía

Estos hallazgos surgieron de la revisión cruzada (auditoría propia) y no estaban en la auditoría manual del equipo. Es la "otra auditoría" que se pidió.

B.1 (M1) seed-demo.mjs exige base vacía y aborta con mensaje claro

Origen: Revisión del seed.  Detalle: Si el usuario ya existe, el seed aborta con El usuario "X" ya existe. El script parte de una base vacía: ejecutar "docker compose down -v" y volver a levantar el stack.  Veredicto: Positivo. Patrón "fail loud" que evita datos corruptos. Referencia de buena práctica para otros scripts del proyecto.

B.2 (M3) ChatSessions.deliver tiene dedupe con eviction bounded

Origen: Revisión de ChatSessions.java.  Detalle: LinkedHashMap con putIfAbsent y eviction al llegar a 4096. Esto previene que un mensaje entregado por Redis y por la propia suscripción local se envíe dos veces. El 4096 es un cap razonable (es ~16 KB de IDs, no es un memory leak).  Veredicto: Patrón a copiar en otros lugares con fan-out (notificaciones push, por ejemplo).

B.3 (M3) PushRepository.subscribe usa lock distribuido en Neo4j

Origen: Revisión de PushRepository.java:22-26.  Detalle: LOCK_USER hace SET u.pushSubscriptionVersion = coalesce(u.pushSubscriptionVersion, 0) + 1. Esto serializa suscripciones concurrentes desde ambas réplicas del backend, evitando race entre subscribe y unsubscribe.  Veredicto: Patrón avanzado, raro de ver en proyectos académicos. Digno de mención en la defensa del proyecto.

B.4 (M4) El SW no loggea tokens (positiva)

Origen: Revisión de frontend/public/sw.js.  Detalle: El Service Worker no escribe el JWT ni la query en ningún cache. Solo guarda metadata del owner (userId + endpoint) y la suscripción push. Si el operador revisa los logs del SW, no ve tokens.  Veredicto: Alineado con H-17 (observabilidad) pero a nivel local. Bien.

B.5 (M5) useRemote hook con cancelaciones consistentes

Origen: Revisión de ChatProvider.tsx:18-23, 49-95.  Detalle: Cada loadHistory(id) arma un AbortController y aborta el anterior con requests.current.get(id)?.abort(). Esto previene race conditions cuando el usuario cambia de conversación rápido.  Veredicto: Patrón defensivo bien aplicado. El useRemote abstrae esto y lo aplica consistentemente.

B.6 (M5) AppLayout remonta ChatProvider con key={session?.token}

Origen: Revisión de AppLayout.tsx.  Detalle: Cuando el usuario cambia (logout + login con otro token), el ChatProvider se desmonta y se vuelve a montar. Esto blinda contra filtrado de sockets, drafts o estados entre cuentas.  Veredicto: Defensa en profundidad notable. No es común ver este nivel de cuidado en proyectos académicos.

B.7 (M6) seed-demo.mjs corre 8 verificaciones Cypher al final

Origen: Revisión del seed (ver B.1).  Detalle: Después de sembrar, el script ejecuta feed, suggestions, mutuals, reach, separation (con y sin camino), discover, thread y aborta si alguna falla. Esto es esencialmente un test de integración del happy path.  Veredicto: Patrón a copiar para futuras features: "si el seed se completa pero las queries fallan, abortar con mensaje claro".

B.8 (M6) Tests de chat cubren casos no triviales

Origen: Revisión de ChatSocketTest.java y ChatResourceTest.java.  Detalle:

persistsBeforePublishingAndDeliversOnceToAllParticipantSessionsOnly: verifica que el mensaje se persiste ANTES de publicarse a Redis, y que solo se entrega una vez aunque haya múltiples sesiones del mismo usuario.

createIsIdempotentInBothDirectionsEvenConcurrently: 6 requests en paralelo creando la misma conversación, verifica una sola.

cursorPaginatesTiesWithoutSkippingOrRepeatingAfterANewMessage: previene el bug clásico de skip/repeat.

failedBroker: mensaje se persiste localmente aunque Redis esté caído.

Veredicto: El test suite más maduro del proyecto. Es una referencia para escribir los tests faltantes en auth y posts (H-25, H-26).

📌 Conclusiones y siguientes pasos

Lo que el sistema hace bien (referencias del equipo, confirmadas por la auditoría cruzada)

Arquitectura por capas limpia y testeable.

Eventos asíncronos para desacoplar push del request.

WebSocket + Redis Pub/Sub bien orquestados.

Web Locks API en el frontend para evitar doble subscribe.

Remount por token en AppLayout y ChatProvider para defensa multi-cuenta.

Seed auto-verificable.

Tests sólidos en chat (concurrencia, expiración, multi-tab, Redis caído).

Lock distribuido en Neo4j para suscripciones push concurrentes.

Nginx con rate limiting diferenciado (auth vs write) y security headers básicos.
