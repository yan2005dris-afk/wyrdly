Informe Priorizado de Auditoría: 9 Hallazgos Clave

Compañeros y docente: compartimos los resultados de la auditoría técnica independiente realizada sobre el repositorio red-social-distribuida. Siguiendo la Regla de Oro de la cátedra, hemos seleccionado de forma consensuada 9 hallazgos prioritarios (H-10, H-11, H-12, H-28, H-05, H-07, H-09, H-22 y H-24) que comprometen la seguridad, la arquitectura por capas, el diseño del dominio, la resiliencia y la interfaz, focalizando el debate de la Fase 2 en problemas de impacto técnico comprobado.

1. Contexto de la Auditoría y Reproducibilidad

Durante el análisis exhaustivo identificamos un total de 28 hallazgos en el sistema (documentados en su totalidad en el informe integral complementario). No obstante, para la interacción en el foro y la apertura de issues para la Fase 2, aplicamos el criterio institucional:

«Una opinión no constituye un hallazgo. Una impugnación sin evidencia no constituye una defensa. La calidad de los argumentos vale más que la cantidad de errores encontrados.»

Por esta razón, este informe se enfoca en los 9 hallazgos seleccionados (1 Crítico, 6 Altos y 2 Medios de arquitectura/dominio). Estos serán los ítems registrados formalmente como GitHub Issues para la réplica del Blue Team.

Resumen de la Misión 1 (FROM ZERO: Reproducibilidad)

  • Resultado del despliegue: Reproducible exitosamente.
  • El comando docker compose up -d --build levanta de manera determinista los 7 contenedores (2 instancias Quarkus, 1 Neo4j, 1 Redis, 1 MinIO, 1 Nginx y el contenedor web).
  • El script scripts/seed-demo.mjs puebla la base de datos y verifica automáticamente las 8 consultas Cypher (C1 a C8), confirmando que las relaciones requeridas por la guía están implementadas.

2. Top 3: Los Problemas Más Relevantes

Conforme a la pauta de la Fase 1, destacamos los tres hallazgos con mayor repercusión sistémica:

TOP 1 · H-10: Clave Privada RSA World-Readable (chmod 644) CRÍTICA

Misión: M4 (Seguridad) | CWE: CWE-732

En docker-compose.yml:102, el contenedor keys-init asigna permisos chmod 644 /keys/* a la clave privada privateKey.pem. Esto permite que cualquier contenedor o proceso con lectura al volumen extraiga la clave y falsifique tokens JWT para cualquier usuario con privilegios totales sin tocar la base de datos.

TOP 2 · H-28: Credencial Inmutable y Sesiones JWT Irrevocables ALTA

Misión: M4 (Seguridad) | CWE: CWE-620

La API no expone ningún endpoint para cambiar o recuperar contraseñas (PUT /auth/password). Además, los JWT tienen una vida útil fija de 24 horas sin lista de revocación ni contador tokenVersion en Neo4j. Si una credencial se filtra, la víctima no puede cambiarla ni expulsar al atacante; el secuestro de la cuenta es definitivo.

TOP 3 · H-11: Enumeración de Usuarios por Timing Attack en Login ALTA

Misión: M4 (Seguridad) | CWE: CWE-208

En AuthService.login(), cuando el usuario no existe, la petición responde en ~5–15 ms (búsqueda vacía). Cuando el usuario existe pero la clave es incorrecta, se ejecuta BcryptUtil.matches tardando 80–120 ms. Esta asimetría medible por latencia permite enumerar toda la base de usuarios mediante un script automatizado.

4. Fichas Técnicas Detalladas (Estructura de GitHub Issues)

A continuación, presentamos el desglose técnico de cada hallazgo con sus pasos de reproducción y recomendaciones:

H-10 · Clave privada RSA del JWT legible por todos (chmod 644)
Misión: M4 Seguridad CWE: CWE-732 / CWE-552
CRÍTICA
Descripción:

El job keys-init asigna permisos 644 (lectura para todo el mundo) sobre las claves criptográficas montadas en el volumen compartido. La clave privada RSA para firmar tokens JWT queda expuesta a cualquier proceso o contenedor que comparta el almacenamiento.

Pasos para reproducir:
  1. Ejecutar docker compose up -d.
  2. Inspeccionar permisos en el contenedor: 
    docker compose exec backend-1 ls -la /keys
  3. Comprobar los permisos del archivo privateKey.pem.
Resultado esperado vs. Obtenido:

Esperado: Permisos estrictos chmod 600 o 640 solo para el usuario del proceso Quarkus.
Obtenido: -rw-r--r-- 1 root root 1675 privateKey.pem (permite lectura a cualquier proceso del host).

Evidencia: 
# docker-compose.yml:102
keys-init:
  image: alpine:3.20
  volumes:
    - app_keys:/keys
  command: |
    sh -c "
      ...
      chmod 644 /keys/*   # <-- Vulnerabilidad crítica
    "
Impacto y Recomendación:

Impacto: Crítico. Falsificación universal de tokens JWT y asunción de privilegios administrativos completos.
Recomendación: Cambiar a chmod 600 /keys/privateKey.pem y asignar propiedad al UID no-root de Quarkus (chown 1001:1001).

H-11 · Enumeración de usuarios por Timing Attack en Login
Misión: M4 Seguridad CWE: CWE-208 / CWE-204
ALTA
Descripción:

El endpoint POST /auth/login responde con tiempos notablemente distintos según la existencia del usuario, permitiendo comprobar usuarios válidos mediante latencias.

Pasos para reproducir: 
# 1. Petición con usuario inexistente:
curl -w "%{time_total}\n" -X POST http://localhost:8080/api/auth/login \
  -H "Content-Type: application/json" \
  -d '{"username":"usuario_fantasma","password":"Password123!"}'
# Retorna en ~5-15 ms

# 2. Petición con usuario real pero clave incorrecta:
curl -w "%{time_total}\n" -X POST http://localhost:8080/api/auth/login \
  -H "Content-Type: application/json" \
  -d '{"username":"ana","password":"Password123!"}'
# Retorna en ~80-120 ms por el cálculo de bcrypt
Evidencia: 
// AuthService.java:51-58
Credentials credentials = repository.findCredentials(request.username())
    .filter(c -> BcryptUtil.matches(request.password(), c.passwordHash()))
    .orElseThrow(() -> new InvalidCredentialsException()); // Cortocircuito rápido
Impacto y Recomendación:

Impacto: Facilita la extracción automatizada del padrón de usuarios para ataques dirigidos.
Recomendación: Ejecutar siempre BcryptUtil.matches contra un hash dummy precargado en memoria cuando el usuario no exista.

H-12 · Ausencia de cabecera Content-Security-Policy (CSP) en Nginx
Misión: M4 Seguridad CWE: CWE-1021 / CWE-79
ALTA
Descripción:

El proxy Nginx no emite la cabecera HTTP Content-Security-Policy. Al almacenar el token JWT en localStorage, cualquier vector XSS en comentarios o nombres permite exfiltrar credenciales hacia servidores externos.

Evidencia: 
# frontend/nginx.conf (líneas 55-57)
add_header X-Content-Type-Options "nosniff" always;
add_header X-Frame-Options "DENY" always;
add_header Referrer-Policy "strict-origin-when-cross-origin" always;
# <-- Falta Content-Security-Policy
Recomendación:

Agregar una política estricta en Nginx restringiendo scripts a 'self' y permitiendo únicamente los endpoints de Web Push autorizados en connect-src.

H-28 · Credencial inmutable: sin cambio de contraseña ni revocación de JWT
Misión: M4 Seguridad CWE: CWE-620 / CWE-613
ALTA
Descripción:

La API no ofrece rutas para modificar contraseñas. Además, los JWT emitidos son válidos por 24 horas (smallrye.jwt.new-token.lifespan = 86400) y no existe lista de revocación en Redis ni versión de token en Neo4j. Al hacer "Cerrar sesión", el frontend solo purga el estado local; el token sigue siendo válido en el servidor.

Evidencia:
  • AuthResource.java:23,36,48: solo expone /registro y /login.
  • AuthProvider.tsx:68-71: logout() solo llama setSession(null) localmente.
  • Ausencia de validación de estado de token en cada petición REST.
Impacto y Recomendación:

Impacto: Secuestro permanente de cuentas ante filtraciones. La víctima no puede expulsar a intrusos.
Recomendación: Agregar tokenVersion en el nodo (:Usuario) e implementar PUT /api/auth/password que incremente este valor para invalidar instantáneamente todos los tokens previos.

H-05 · Acoplamiento excesivo y orquestación monolítica en PostService
Misión: M3 Código CWE: Arquitectura / God Service
ALTA
Descripción:

PostService concentra 5 colaboradores directos y su método create() (46 líneas) coordina validaciones de texto, llamadas a MinIO, persistencia en Neo4j, publicación de eventos CDI y rollback manual en 4 bloques try/catch.

Evidencia: 
// PostService.java:21-26
public PostService(PostRepository repository, MediaStorage storage,
                   ImageValidator images, Event<PostCreated> events,
                   PostAssembler assembler) { ... }
Impacto y Recomendación:

Impacto: Alto blast radius y riesgo de regresión al mezclar almacenamiento multimedia con persistencia de grafos.
Recomendación: Descomponer en PostCreator, PostImageAttacher y PostPersister con responsabilidades aisladas.

H-07 · Acoplamiento transitivo: AuthService depende de UserService en vez de UserRepository
Misión: M3 Código CWE: Arquitectura / Violación DIP (Dependency Inversion)
MEDIA
Descripción:

AuthService inyecta directamente la clase de servicio UserService en lugar de consultar la capa de persistencia UserRepository. Durante el registro (register()), delega en users.profile(id) para construir la respuesta.

Evidencia: 
// backend/src/main/java/com/redsocial/auth/AuthService.java:23-26, 32-49
public AuthService(AuthRepository repository, UserService users) {
    this.repository = repository;
    this.users = users;
}

public Profile register(RegisterRequest req) {
    // ... crea usuario en AuthRepository ...
    return users.profile(id);
}
Impacto:

Genera acoplamiento transitivo innecesario entre dos servicios del mismo nivel. Si UserService en el futuro incorpora dependencias adicionales (notificaciones, auditoría, caches), arrastra ese peso directamente a AuthService. Dificulta los tests unitarios aislados del módulo de autenticación y aumenta el radio de explosión ante cambios.

Recomendación:

Hacer que AuthService consulte directamente a UserRepository para obtener la proyección de perfil mínima (que ya utiliza para persistir), o extraer un ensamblador/puerto compartido (ej. UserProfileReader) para desacoplar ambos servicios.

H-09 · Deuda técnica por spanglish estructural y ruptura de lenguaje ubicuo (DDD)
Misión: M3 Código CWE: Deuda Técnica / Inconsistencia de Dominio
MEDIA
Descripción:

Existe una mezcla continua y desordenada de español e inglés a lo largo del backend y el frontend, rompiendo el principio fundamental de Lenguaje Ubicuo (DDD):

  • Paquetes en español: comentarios, notificaciones, con clases como ClavePublica.java, SuscripcionRequest.java, Sugerencia.java.
  • Records con campos en español: CommentRequest(texto, respondeA), CommentResponse(texto, fecha, autor, respuestas).
  • Métodos en inglés sobre esos mismos objetos: create(), thread(), save(), history().
  • Comentarios y logs en inglés: // Shares the /posts root..., conviviendo con respuestas al usuario en español (mensaje en lugar de message).
Evidencia: 
// backend/src/main/java/com/redsocial/comentarios/CommentRequest.java
public record CommentRequest(String texto, String respondeA) {}

// backend/src/main/java/com/redsocial/comentarios/CommentService.java
public CommentResponse create(String autorId, CommentRequest request) { ... }
public List<CommentResponse> thread(String postId) { ... }

// backend/src/main/java/com/redsocial/notificaciones/Sugerencia.java
package com.redsocial.notificaciones;
Impacto:

Duplica el costo cognitivo de los desarrolladores al tener que adivinar si un atributo es text o texto, parentId o respondeA. Genera fricción en integraciones, aumenta la propensión a bugs en refactorizaciones y deteriora la consistencia de la arquitectura.

Recomendación:

Establecer y documentar una política estándar en el repositorio:
1. Código interno (100% inglés): Nombres de paquetes, clases, records, métodos, variables, comentarios y commits (ej. CommentRequest(text, parentId)).
2. Capa de usuario/API: Mensajes de error en español y descripciones localizadas.
3. Congelar la regla para código nuevo e integrar la migración progresiva en refactors futuros.

H-22 · Pantalla en blanco (White Screen of Death) en comentarios
Misión: M5 UX / UI Crash CWE: CWE-754 / CWE-248
ALTA
Descripción:

CommentThread.tsx accede directamente a propiedades anidadas (comment.autor.id, comment.autor.username) asumiendo que el autor siempre existe. Ante un comentario huérfano o un usuario eliminado en el grafo, JavaScript lanza un TypeError: Cannot read properties of undefined. Al no existir ningún ErrorBoundary en toda la aplicación React, React desmonta el árbol completo del DOM, dejando la pantalla totalmente en blanco.

Evidencia: 
// CommentThread.tsx:31-50
const profilePath = "/usuarios/" + encodeURIComponent(comment.autor.id);
const firstName = comment.autor.nombre.split(" ")[0];
...
<span className="muted break-all">@{comment.autor.username}</span>
Recomendación:

1. Envolver la jerarquía de rutas en componentes <ErrorBoundary> con fallback amigable.
2. Usar optional chaining: comment.autor?.username ?? copy.deletedUser.

H-24 · Ausencia de Circuit Breaker y Timeout en driver Neo4j
Misión: M6 Resiliencia CWE: CWE-400 / Resiliencia Distribuida
ALTA
Descripción:

Las consultas al grafo carecen de límites de tiempo de espera y disyuntor ante fallos. Si Neo4j se pausa (docker compose pause neo4j) o se satura, las peticiones entrantes en Quarkus quedan bloqueadas hasta agotar los hilos de eventos de Netty, provocando caídas en cascada de ambas réplicas y errores 504 Gateway Timeout en Nginx.

Recomendación:

Integrar quarkus-smallrye-fault-tolerance con anotaciones @Timeout(value = 3, unit = SECONDS) y @CircuitBreaker(failureRatio = 0.5) en los repositorios de lectura.
